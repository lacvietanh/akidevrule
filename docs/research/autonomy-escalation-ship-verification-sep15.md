# Research — over-strict autonomy: literal-token gate, resident ask-bias, no deep-think trigger, no post-push CI

**Start time:** 2026-09-15, immediately after owner feedback on a week of `/akiship`/release sessions.

## 1. Initial purpose

The owner reported four symptoms in one sitting: an explicit "release trọn vẹn" order was refused for lacking the literal `/akiship` token; a run asked whether to run an additive migration that `stack.C8` had already answered; he kept re-typing "/akithink 4-6 rounds" by hand because no mechanism made deep-think fire on hard cases on its own; and CI failures on GitHub went unnoticed after a push. Context at the time: `release.B8`/`skills/akiship/SKILL.md` carried the literal-token gate shipped by `akiship-literal-activation-aug22.md`; `agent.B3`'s ask-before list is a core `@` import while `stack.C8`/`coding.B5` (the permission-to-act counterweight) load only contextually; `METHOD-deep-think.md` had passive (auto, inline) and active (`/akithink`, explicit) modes only; `coding.B3` classed a full build as user-triggered with no exception for shipping, and `release.B7`/C5 verified deploy only for stacks that deploy on push.

## 2. Strategy

Root-cause each symptom against the exact files in the failure chain, checking whether it is a load-fail (rule absent) or a comply-fail (rule present, mis-weighted or contradicted by another rule) — the same discriminator used in `akiship-literal-activation-aug22.md`. Where two guard-shaped fixes compete (rewrite a gate vs. state a counterweight), prefer the counterweight so the meta-cause (every act-wrongly incident added a strongly-worded guard, every over-asking incident only added soft prose) does not repeat.

## 3. Checklist

1. Re-read `akiship-literal-activation-aug22.md` in full to determine whether the literal token was load-bearing or added only false negatives against the incident it was written for.
2. Trace `agent.B3`'s ask-before list against `stack.C8`/`coding.B5`'s permission-to-act residency to check for the same asymmetry, inverted.
3. Read `release.B8`'s self-answer bullet and check whether "owner-worded criteria" wording produced the redundant migration question.
4. Check `METHOD-deep-think.md`'s two consumption modes and `akirule/SKILL.md`'s deep-think routing for a resident, non-interactive trigger.
5. Check `coding.B3` and `release.B7`/C5 for a build/test step and a post-push CI check applicable to non-deploying repos (CLI, library, npm package).

## 4. Result

**Symptom 1 — literal-token gate over-corrected.** `commit 1b9560a`'s incident phrase ("tóm lại cần làm gì để trọn vẹn") already fails two independent conditions — no release object, and interrogative rather than imperative — so the literal-token requirement added on top caught no additional failure mode and only produced false negatives against a plainly-worded release order such as "release trọn vẹn đi". The mechanical part worth keeping is the release-object check (a release-flavored paraphrase alone is not an order); the literal-token requirement is not.

**Symptom 2 — residency asymmetry, inverted.** `agent.B3`'s ask-before list ("destructive or hard-to-reverse actions") is a core `@` import, resident every session. The rule that actually answers most of those cases — `stack.C8`'s execution-ownership clause, `coding.B5`'s ladder — loads only on a stack/coding signal match. A session holding only the resident list reads every hard-to-reverse-looking action as needing to ask, because the counterweight that would resolve most of them was never in context. This is the same shape as `core-floor-promotion-aug6.md` and `akiship-literal-activation-aug22.md` (a guarantee whose mechanism cannot deliver it), applied to the opposite failure direction — under-acting instead of over-acting.

**Symptom 3 — B8's self-answer licence collided with owner-worded-criteria wording.** The prior wording ("this licence covers facts the repo determines, never what the owner meant… when it is the owner's own wording that is ambiguous, that is the one question worth the interrupt") reads a run-of-the-mill repo-answered question (does this migration run) as ambiguous owner wording whenever the owner's release order used an intensity word, producing exactly the redundant ask the owner reported.

**Symptom 4 — no resident deep-think trigger, no non-interactive mode.** `METHOD-deep-think.md` A2 had exactly two consumption modes: passive (inline, at most one clarifying question, keyword-routed through `akirule`) and active (`/akithink`, fully interactive, explicit-invoke only). Neither mode fires deep-think deterministically on a hard case without the owner naming it — passive is shallow by design, active needs an explicit invocation. The owner's repeated "/akithink 4-6 rounds" typing was him manually supplying both the trigger and a fixed round count neither mode offered.

**Symptom 5 — verification-tier gap plus a CI-watch gap that only ever covered deploying stacks.** `coding.B3` classed "a full build and the test suite" together with dev servers and live network calls as user-triggered, so nothing built locally before a push even at ship time. `release.B7` had six steps ending at verification honesty and version decision, with no build/test step at all. Post-push checks existed only as `release.C5` (stack deploy verification, ⟨Aki⟩-web-specific) — a CLI, library, or npm-package repo had no post-push check of any kind, so a red GitHub Actions run could sit unnoticed indefinitely.

**Meta-cause, cutting across all five:** every incident where the agent acted wrongly (the aug22 push) produced a strongly-worded, resident guard; every incident where the agent over-asked only ever produced soft prose (kill-tests, B5's ladder) that competed for attention against the guard rather than outranking it in the same location. Guard wording accumulated; permission wording did not.

## 5. Decision

**Action** — implemented directly in the working tree (already present at task start, this record documents it); execution record: [plan/done/autonomy-escalation-ship-verification.md](../plan/done/autonomy-escalation-ship-verification.md).

- `payload/METHOD-deep-think.md` — A2 gains a third mode, **triggered self-run**, fired by the new `agent.A3` triggers or owner authorization, non-interactive, depth scaled to difficulty rather than a fixed round count; the radar section (previously "offer `/akithink`") now says an autonomous run does not stop to offer an interactive session, it runs the depth itself and decides.

**Rejected alternatives:**
- Keep the literal `/akiship` token requirement — produces false negatives on a plainly-worded release order and the aug22 incident it defends against is already blocked by the release-object and imperative conditions independently.
- Force-load `METHOD-deep-think.md` every session (make it a fourth core `@` import) — token cost on every trivial task; the fix is resident **triggers** in `agent.A3` (already core), not a resident **method file**, which still loads on trigger.
- A fixed "4–6 rounds" depth for triggered self-run — depth should scale to the difficulty of the specific case, not a constant the owner has to keep re-specifying.
- Rely only on post-push CI (B10) and skip local build/test at ship time — wastes a full push cycle and leaves public red CI history visible before the failure is caught; local build/test mirroring CI catches most failures before they are ever pushed, and B10 exists specifically to catch only the residue CI checks that cannot be reproduced locally (OS-matrix legs, secrets-gated jobs).
- Run a full build after every single edit — RAM/time/token cost on a 16GB-class development machine; typecheck/lint is the correct edit-time tier, full build is reserved for the batch/ship moments.

**Critique recorded:** `akiship-literal-activation-aug22.md` itself noted that `agent.A3` was resident and still misfired on the original incident, so imperative-detection is judgment, not a mechanical guarantee — the release-object condition kept in this round's gate wording is the part that is actually mechanical (a check on the presence of a release-flavored word/token), and it is retained precisely because it is the load-bearing half; the literal-token half was the judgment-adjacent half masquerading as mechanical, which is why removing it does not reopen the original incident.
